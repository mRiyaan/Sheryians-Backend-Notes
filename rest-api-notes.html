Understanding REST APIs

Representational State Transfer & the 5 core pillars

REST (Representational State Transfer) is an architectural style for designing networked applications. It relies on stateless, client-server communication over HTTP using standard methods and status codes. RESTful APIs are designed around resources — which can be anything from users and products to documents.

Key Concepts

  1. Resources: Everything that can be accessed via a RESTful API is considered a resource. Each resource has a unique identifier (URI).
  2. Representations: Resources are transferred in some representation such as JSON or XML.
  3. Stateless Communication: Each request from client to server contains all the information needed. The server does not store any state about the client session.
  4. HTTP Methods: REST APIs use standard HTTP methods to perform actions on resources.
  5. HTTP Status Codes: Servers use HTTP status codes to indicate the outcome of a client's request.
02

HTTP Methods

Actions, Idempotence, and Safety

An HTTP method defines the action you want to perform on a resource. These are the most commonly used ones:

MethodDescriptionIdempotent?Safe?
GET Retrieves a resource or a list of resources. Should not modify data on the server. Yes Yes
POST Creates a new resource. The request body contains the data for the new resource. No No
PUT Updates a resource by replacing it entirely. Requires the complete new representation in the request body. Yes No
PATCH Updates a resource by partially modifying it. Requires only the modified fields in the request body. No* No
DELETE Deletes a resource. Yes No

* PATCH is not guaranteed to be idempotent. It can be written in an idempotent way (setting a field to a fixed value), but a patch like "increase price by 10" changes the result every time it runs.

Idempotence

An idempotent method produces the same end result whether it is called once or many times with the same request. GET, PUT, and DELETE are idempotent. POST is not — calling it twice creates two resources.

Safe Methods

A safe method must not modify data on the server; it is read-only. GET, HEAD, and OPTIONS are safe methods. Every safe method is automatically idempotent, but the reverse is not true.

RESTful API Design Best Practices

7 golden rules for clean, predictable endpoints
  • Use nouns to represent resources — /users, /products — never verbs like /getUsers.
  • Use plural nouns for collections — /users, and /users/:id for a single item.
  • Use HTTP methods according to their semantics (GET for read, POST for create, and so on).
  • Use status codes appropriately to convey the outcome of the request.
  • Keep your APIs consistent and predictable across every route.
  • Design stateless APIs that do not rely on session storage on the server.
  • Version your API (/api/v1/users) so future changes do not break existing clients.
05

Interview Questions and Answers

10 high-frequency REST API questions with model answers
Q1What is a REST API?
REST (Representational State Transfer) is an architectural style for designing networked applications. It relies on stateless client-server communication using standard HTTP methods and status codes. RESTful APIs are designed around resources, which can be accessed using methods like GET, POST, PUT, PATCH, and DELETE.
Q2What are the common HTTP methods used in REST APIs, and what do they mean?
  • GET — retrieve a resource or a list of resources.
  • POST — create a new resource.
  • PUT — update a resource by replacing it with new data.
  • PATCH — update a resource by partially modifying it.
  • DELETE — delete a resource.
Q3Explain the difference between PUT and PATCH.
  • PUT — used to completely replace a resource. It expects the entire resource representation in the request body. Any field you leave out gets wiped.
  • PATCH — used to partially modify a resource. It only requires the fields that need to be updated in the request body.
Q4What are HTTP status codes, and why are they important in REST APIs?
HTTP status codes are three-digit numbers the server sends to the client to indicate the outcome of a request. They are important because they let the client understand whether a request succeeded, failed, or needs further action — without having to parse the response body. They also help a lot while troubleshooting API issues.
Q5Give some examples of common HTTP status codes and when they are used.
  • 200 OK — the request was successful (for example, retrieving a resource).
  • 201 Created — a new resource was successfully created (for example, a POST request).
  • 400 Bad Request — the request was invalid.
  • 401 Unauthorized — the client needs authentication (API key or credentials).
  • 403 Forbidden — the client is authenticated but does not have permission to access the resource.
  • 404 Not Found — the resource does not exist.
  • 500 Internal Server Error — a server-side error occurred.
Q6What does it mean for a method to be idempotent? Which HTTP methods are idempotent?
An idempotent method produces the same result on the server regardless of how many times it is called with the same request. GET, PUT, and DELETE are idempotent. POST is not, because each call creates a new resource. PATCH is not guaranteed to be idempotent — it depends entirely on how the patch operation is written.
Q7What does it mean for a method to be safe? Which HTTP methods are safe?
A safe method must not modify any data on the server — it is purely read-only. GET, HEAD, and OPTIONS are safe methods.
Q8If an API operation fails, should the API return an error status code?
Yes. An API should always return a proper error status code along with a descriptive message. For example: use 400 Bad Request for invalid request data, 404 Not Found if the resource is unavailable, and 500 Internal Server Error when an unexpected error happens on the server.
Q9What are some best practices for designing RESTful APIs?
Use nouns to represent resources and pluralise collections; use HTTP methods according to their semantics; use status codes appropriately; keep your APIs consistent and predictable; and design stateless APIs.
Q10How do you handle errors in RESTful APIs?
Use proper HTTP status codes to indicate the type of error, include a descriptive error message in the response body (usually JSON), keep the error shape consistent across the whole API so the frontend can handle it in one place, and log errors on the server side for debugging.
