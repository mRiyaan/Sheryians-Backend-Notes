First things first — what is backend?

Client vs Server & the apartment building analogy

When you open Instagram, you see photos, likes, and comments. None of that is already stored on your phone. Your phone asks another computer for it, and that computer sends it back.

Client

The one who asks. Your browser, a mobile app, or a tool like Postman.

Server

The one who gives. A program that stays switched on and keeps listening.

Backend is the code that runs on the server. That is exactly what you are learning to write now.

It will come back again and again throughout these notes.

02

What is HTTP?

HyperText Transfer Protocol & Statelessness

HTTP stands for HyperText Transfer Protocol. The word protocol simply means a set of rules.

Imagine walking into a shop and saying, "One packet of biscuits, please." The shopkeeper understands you because both of you speak the same language. In the exact same way, the client and the server need one fixed language to talk in. That language is HTTP.

The rules of HTTP decide:

  • What format a request must be sent in
  • What format the response will come back in
  • Which action uses which method — GET, POST, PUT, DELETE
  • How the server tells you whether the job succeeded — the status code
HTTP is stateless

The server does not remember what you asked for last time. Every request is treated as a completely fresh conversation. That is why you have to send your identity (a token) along with every single request. This will make much more sense when you reach the login and JWT topic.

HTTP vs HTTPS (HTTPS = HTTP + Secure)

HTTP (Postcard)

Data travels as plain text. Anyone sitting in the middle — a hacker, or the owner of the WiFi you are using — can read your password clearly.

HTTPS (Sealed Envelope)

The same data travels encrypted, that is, locked. Anyone in the middle sees only meaningless symbols.

Every real website today runs on HTTPS. While developing on your own laptop (localhost), plain HTTP is perfectly fine.

03

Request and response — the full cycle

Anatomy of HTTP messages and status code families
A request has 4 parts
  1. Method — what to do (GET / POST / PUT / DELETE)
  2. URL — on which resource (/users, /users/5)
  3. Headers — extra information (token, content-type)
  4. Body — the actual data (only in POST and PUT)
A response has 3 parts
  1. Status code — did the job succeed or not
  2. Headers — information about the response
  3. Body — the actual data (JSON or HTML)

Status codes — an easy way to remember them

RangeMeaningCommon Codes
2xxEverything went fine200 OK · 201 Created
3xxGo somewhere else301 · 302 Redirect
4xxThe client made a mistake400 Bad Request · 401 Unauthorized · 404 Not Found
5xxThe server made a mistake500 Internal Server Error
Remember it in one line

4xx means you messed up. 5xx means I (the server) messed up.

04

What is a port, and why do we need it?

0 to 65535 doors on your machine

Many programs can run on your computer at the same time — a React app, a backend server, a database. So when a request arrives at your computer, how does the computer know who it is meant for? A port solves exactly this confusion.

http://localhost:4567 literally means: go to this same computer (127.0.0.1), and knock on the door of flat number 4567.

PortUsed By
80Default for HTTP
443Default for HTTPS
27017MongoDB
3000 / 5000 / 8080Development servers (by convention)
Two important points

1. Ports 0 to 1023 are reserved for the system — pick any number above 3000 for your projects.
2. Since 80 and 443 are defaults, you never have to type a port when visiting https://google.com — the browser adds :443 automatically.

An error you will definitely see

EADDRINUSE: address already in use — It means somebody already lives in that flat. Either close the old terminal (Ctrl + C) or use a different port.

05

What does listen() actually do?

Raising the shop shutter and keeping the event loop alive

Simply creating a server does nothing on its own. Opening a shop is not enough — you also have to raise the shutter.

server.listen(4567) means: "I am now sitting at the door numbered 4567. From this moment on, I will keep listening for anyone who rings the bell."

One thing you should notice

Once listen() runs, the program does not exit. A normal JavaScript file prints something and quits immediately, but a server file keeps running — because it is waiting. To stop it, press Ctrl + C in the terminal.

06

Your first server — line by line

Using Node's built-in http module
const http = require("http");
const PORT = 4567;

const server = http.createServer((req, res) => {
  console.log("hello i m server"); // prints in YOUR terminal, not browser!
  res.end("ok mene tumhari baat sun li");
});

server.listen(PORT, () => {
  console.log(`Server running on http://localhost:${PORT}`);
});
  • require("http") — Fetches Node's built-in HTTP module (no npm install needed).
  • http.createServer((req, res) => { ... }) — Runs once for every request that arrives. req holds what the client sent; res sends the answer back.
  • res.end(...) — Sends the response and closes the conversation. One request gets exactly one response.
07

What is the problem with the raw http module?

Why every backend developer switched to a framework
const server = http.createServer((req, res) => {
  if (req.url === "/" && req.method === "GET") {
    res.end("Home page");
  } else if (req.url === "/users" && req.method === "POST") {
    let raw = "";
    req.on("data", (chunk) => { raw += chunk; });
    req.on("end", () => {
      const body = JSON.parse(raw); // parse chunks by hand!
      users.push(body);
      res.writeHead(201);
      res.end("User created");
    });
  } else {
    res.writeHead(404);
    res.end("Not found");
  }
});
1. Manual routing: One if-else branch per route. 50 routes = 50 unreadable branches.
2. Manual body chunking: JSON arrives in small stream chunks; you have to join them and call JSON.parse manually.
3. No dynamic URLs: Extracting 5 out of /users/5 requires manual string slicing.
4. No middleware system: Common checks like auth have to be copy-pasted everywhere.
08

What is Express.js?

A minimal framework built on top of Node's http module

Express does nothing magical — internally it still uses Node's http module. If raw http is kneading dough and rolling rotis by hand, Express is a roti-maker machine: work that took 100 lines now takes 10.

npm init -y
npm install express
  • Clean routing with app.get(), app.post(), app.put(), app.delete()
  • Dynamic route parameters out of the box (/users/:id)
  • A composable middleware pipeline
  • Ready-made helpers: res.json(), res.status(), res.send()
  • Single-line body parsing via express.json()

The same server in Express

Clean routes and response helpers
const express = require("express");
const app = express();
const PORT = 4567;

app.get("/", (req, res) => {
  res.send("Hello from Express");
});

app.get("/about", (req, res) => {
  res.send("This is the about page");
});

app.listen(PORT, () => {
  console.log(`Server running on http://localhost:${PORT}`);
});
Method on resWhat it does
res.send("hi")Send anything — a string, object, or array
res.json({ a: 1 })Send JSON — use this when building an API
res.status(404)Set status code (must chain onto .json() or .send())
res.status(201).json({...})Set status code and send JSON together — the most common pattern
res.end()Close the response without sending any data

What is CRUD?

Create · Read · Update · Delete
LetterOperationHTTP MethodExample
CCreate — make something newPOSTA new user signs up
RRead — view somethingGETOpening a profile
UUpdate — change somethingPUT / PATCHEditing your bio
DDelete — remove somethingDELETEDeleting an account
Never put the action inside the URL

Wrong: /getUsers · /createUser · /deleteUser
Right: GET /users · POST /users · DELETE /users/5
A URL should name the thing (a plural noun), never the action (a verb).

A complete CRUD API with user data

Interactive Express Route Simulator + Full Code
Interactive Express CRUD Simulator Live Request Tracer
// Click any route above to trace how Express extracts input, validates, and responds. Status: 200 OK Response JSON: [ { "id": 1, "name": "Aarav", "age": 19, "city": "Indore" }, { "id": 2, "name": "Priya", "age": 20, "city": "Bhopal" } ]
const express = require("express");
const app = express();

app.use(express.json()); // needed to read req.body - keep ABOVE routes!

let users = [
  { id: 1, name: "Aarav", age: 19, city: "Indore" },
  { id: 2, name: "Priya", age: 20, city: "Bhopal" },
];

// READ ALL
app.get("/users", (req, res) => {
  res.status(200).json(users);
});

// READ ONE
app.get("/users/:id", (req, res) => {
  const id = Number(req.params.id); // string -> number!
  const user = users.find((u) => u.id === id);
  if (!user) return res.status(404).json({ message: "User not found" });
  res.status(200).json(user);
});

// CREATE
app.post("/users", (req, res) => {
  const { name, age, city } = req.body;
  if (!name || !age) {
    return res.status(400).json({ message: "name and age are required" });
  }
  const newUser = { id: users.length + 1, name, age, city };
  users.push(newUser);
  res.status(201).json(newUser);
});

// UPDATE
app.put("/users/:id", (req, res) => {
  const id = Number(req.params.id);
  const index = users.findIndex((u) => u.id === id);
  if (index === -1) return res.status(404).json({ message: "User not found" });
  users[index] = { ...users[index], ...req.body, id };
  res.status(200).json(users[index]);
});

// DELETE
app.delete("/users/:id", (req, res) => {
  const id = Number(req.params.id);
  const index = users.findIndex((u) => u.id === id);
  if (index === -1) return res.status(404).json({ message: "User not found" });
  const removed = users.splice(index, 1);
  res.status(200).json({ message: "Deleted", user: removed[0] });
});

app.listen(4567, () => console.log("Server ready on 4567"));
Every route follows the same 4-step pattern

1. Extract the input (params / body / query) → 2. Check whether it is valid → 3. Do the actual work → 4. Send a response with the right status code (using return on early errors so you never trigger Cannot set headers after they are sent to the client).

12

What is middleware?

The college gate guard standing between request and route handler

Middleware is a function that runs in between — after the request arrives from the client, but before it reaches your route.

app.use((req, res, next) => {
  console.log(req.method, req.url, new Date().toLocaleTimeString());
  next(); // <- forget this and the request hangs forever!
});
  • req — the request object (you can attach data like req.user).
  • res — the response object (you can stop the request early with an error response).
  • next() — "I am done, pass it along to the next function."
13

express.json() — the middleware you cannot skip

Turning raw network byte chunks into req.body

Without app.use(express.json()), req.body is undefined because JSON travels over the network as raw byte chunks. express.json() joins the chunks, checks for Content-Type: application/json, runs JSON.parse(), and populates req.body.

app.use(express.json());                         // for JSON payloads
app.use(express.urlencoded({ extended: true })); // for HTML <form> payloads

15

Mistakes everybody makes

7 classic bugs and how to fix them in seconds
1. Writing express.json() below the routes → req.body comes out undefined.
2. Treating req.params.id as a number → Always wrap in Number(req.params.id).
3. Forgetting return before res.status(404).json() → Triggers "Cannot set headers after they are sent".
4. Forgetting next() inside middleware → The request hangs forever.
5. Getting EADDRINUSE → Close the old terminal or change the port.
6. Selecting Text instead of JSON in Postman → Body arrives empty.
7. Not restarting the server after code changes → Use nodemon server.js.
